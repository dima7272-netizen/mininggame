# Баланс-центр Dig Get Stronger

Рабочий браузерный сервис для ежедневной настройки игровых конфигов без Google Sheets, Excel и Roblox Studio. Он импортирует текущие 9 JSON, сохраняет большие числа без преобразования в JavaScript `number`, связывает игровые сущности, создаёт неизменяемые версии и проводит одну и ту же версию через DEV, подтверждение теста и PROD.

DEV подключается через GitHub: сервис атомарно создаёт commit в `main`, обновляет `.deploy/dev.json`, ждёт GitHub Actions и считает публикацию успешной только после обратного чтения конфигов из Roblox. Без токена с правом Write кнопка блокируется; ложного успешного DEV больше нет. PROD выключен по умолчанию отдельным флагом.

## Возможности

- русскоязычная адаптивная панель, светлая и тёмная темы, заметный DEV/PROD;
- связанные редакторы Rooms + RoomDrops + SellItems, Pickaxes, Pets, Upgrades, Rebirth, Arenas и Spiders;
- тепловая карта 75 наград × 46 комнат с закреплёнными заголовками, точным редактированием процентов, жизненными циклами и сравнением соседних комнат;
- отдельная аналитика: сравнение выбранных наград, состав комнаты, десять настоящих игровых rarity-групп, ожидаемая цена, HP против награды, шанс новизны, активные/новые/последние типы и доля устаревших предметов;
- блокировки ячеек, нормализация до 100%, отмена/повтор, копирование и перенос схемы, массовые правки и предварительное сравнение;
- объяснимые предложения по балансу и детерминированный генератор на шаблонах «Плавный», «Стандартный» и «Быстрый»;
- основной стандарт наград: точный цикл `1 → 2 → 3 → 5 → 8 → 12 → 17 → 23 → 29% → 0%`; резкое удаление разрешается только при достаточной более сильной замене без ухудшения ожидаемой ценности;
- несколько новых наград получают не меньше 1% каждая; при несовместимом лимите активных типов генератор просит разнести появления, а не создаёт нулевые шансы и разрывы;
- универсальный raw JSON-редактор для текущих и будущих конфигов;
- десятичная точность через `lossless-json` и `decimal.js`, логарифмические графики;
- 3 уровня проверок: ошибка, предупреждение, наблюдение;
- массовая нормализация весов с блокировкой строк, preview и подтверждением;
- пользовательские цели баланса без выдачи неподключённых формул за факты;
- неизменяемые снимки, SHA/checksum, ZIP-экспорт каждой версии и откат новой версией;
- закрытая регистрация, приглашения с ролью, допправами, TTL, лимитом использований и отзывом;
- безопасный маршрут `черновик → DEV → подтверждение тестирования → отдельное подтверждение PROD`;
- D1-журнал операций с автоматическим скрытием токенов, ключей и Authorization.

## Локальный запуск

Требования: Node.js 22.13+ (рекомендуется 24), Corepack и pnpm.

```bash
cd tools/balance-console
corepack enable
pnpm install --frozen-lockfile
cp .env.example .env.local
pnpm dev
```

Для настоящего DEV используйте авторизацию GitHub CLI. Токен передаётся только дочернему процессу и не записывается в `.env` или базу:

```bash
gh auth login
pnpm dev:github
```

Аккаунту GitHub нужна роль **Write** в `dima7272-netizen/mininggame`. При наличии только чтения сервис покажет имя аккаунта и заблокирует публикацию.
В Actions этого же репозитория должен существовать секрет `ROBLOX_API_KEY`; значение никогда не читается обратно и не попадает в сервис или базу.

Откройте `http://localhost:3000`. На опубликованном сервисе первый пользователь создаёт аккаунт владельца по имени, email и паролю. После этого регистрация доступна только по ссылке из раздела «Команда и права». В development сохраняется локальный владелец `owner@dig.local` для тестирования игровых экранов.

Пароли хешируются PBKDF2-SHA-256 с индивидуальной солью. В D1 хранятся только хеши паролей и хеши случайных токенов сессий; браузер получает защищённую HttpOnly-cookie с ограниченным сроком действия.

Проверки:

```bash
pnpm exec tsc --noEmit
pnpm lint
pnpm test
pnpm test:e2e:install  # один раз на машине
pnpm test:e2e
pnpm build
```

Docker собирается из корня репозитория, потому что seed читает `configs`:

```bash
docker build -f tools/balance-console/Dockerfile -t dig-balance .
docker run --rm -p 3000:3000 dig-balance
```

## Архитектура и данные

Сервис создан внутри существующего репозитория, так как готового web-приложения не было. Использованы Next/Vinext + TypeScript, React, D1/SQLite и Drizzle. D1 выбран вместо отдельного PostgreSQL для совместимости с локальным Sites runtime и простой поставки; все доменные таблицы содержат `game_id`, поэтому модель допускает несколько игр, хотя UI сейчас открывает только `dig-get-stronger`.

Основные таблицы:

- `games`, `game_settings`, `users`, `game_members` — игры, настройки, аккаунты и роли;
- `versions` — неизменяемые JSON-снимки, база/SHA, автор, результат проверок, статус и checksum;
- `deployments`, `environment_snapshots` — DEV/PROD операции и перечитанные снимки;
- `invitations` — только SHA-256 токена, TTL, лимит и отзыв;
- `audit_logs` — действия без секретов;
- `balance_goals` — пользовательские цели, которые не участвуют в расчёте без подтверждённой формулы.

Инициализация development-схемы идемпотентно выполняется в `db/runtime.ts`. Проверяемые миграции находятся в `drizzle/`:

```bash
pnpm db:generate
# Для удалённой D1 после подстановки настоящего имени/ID базы:
pnpm exec wrangler d1 execute <DB_NAME> --remote --file drizzle/0000_wide_proemial_gods.sql
pnpm exec wrangler d1 execute <DB_NAME> --remote --file drizzle/0001_living_randall.sql
```

## Импорт и повторный импорт

`scripts/generate-seed.mjs` читает все `../../configs/*.json`, сортирует их по имени и генерирует `lib/generated/seed-configs.ts` с исходными строками и текущим Git SHA. Он выполняется перед `dev` и `build`.

Повторный импорт не заменяет данные молча: обновите `configs`, выполните `pnpm seed:generate`, откройте сравнение источников и сохраните новую версию. Табличный preview остаётся отдельным наблюдаемым источником; конфликт Spiders требует ручного выбора владельца.

ZIP-экспорт версии содержит `configs/<Name>.json` и `manifest.json`. Семантический round-trip, большие числа, 9 конфигов, 46 сумм весов и внешние ссылки покрыты тестами.

### Настоящие иконки наград

Авторское соответствие `itemId → rbxassetid` прочитано без изменений игры из `ReplicatedStorage.Game.Selling.SellItemConfig` в PROD place `104830450645212`. Дополнительно прочитаны 55 иконок кирок из `PickaxeConfig`, 10 питомцев из `PetConfig` и 4 улучшения из `UpgradeConfig`. Манифесты находятся в `data/item-icons.json` и `data/entity-icons.json`, а 144 стабильных PNG — в `public/item-icons/` и `public/entity-icons/`. Интерфейс не зависит от временных Roblox CDN-ссылок: карта наград, каталог цен, соседние комнаты, аналитика, предложения, история версий и редакторы кирок, питомцев и улучшений используют общие локальные компоненты иконок.

### Настоящие группы наград

Порядок, названия и цвета десяти групп прочитаны из `ReplicatedStorage.Game.Rarities.RarityConfig`, а принадлежность всех 75 предметов — из поля `rarity` в `ReplicatedStorage.Game.Selling.SellItemConfig` версии place 89. Манифест `data/reward-groups.json` различает `Godly` и `Divine`, проверяет полное распределение без дублей и используется в тепловой карте, соседних комнатах, каталоге, аналитике и отдельной вкладке «Группы наград».

Повторная загрузка отсутствующих файлов и полная проверка:

```bash
pnpm icons:import
pnpm icons:verify
```

Команда импорта не трогает уже корректные PNG. Для каждого SellItems ID проверяются Roblox asset ID, PNG-сигнатура и локальный путь; вкладка «Проверка иконок» показывает найденные и отсутствующие изображения. Не найденная иконка отображается нейтральным `?` и не ломает таблицу.

## Роли

| Роль | Базовые права |
|---|---|
| Владелец | все атомарные права |
| Администратор | просмотр/редактирование/импорт, подключения и пользователи |
| Балансировщик | просмотр и редактирование |
| Тестировщик | просмотр, DEV и подтверждение теста |
| Издатель PROD | просмотр, PROD и откат |
| Наблюдатель | только просмотр |

При приглашении можно добавить отдельные права поверх роли. Токен показывается один раз; в D1 хранится только SHA-256. Открытая регистрация выключена.

## DEV → PROD

1. Сохранение создаёт новую неизменяемую версию; устаревшие `baseVersionId` и Git SHA отклоняются.
2. Блокирующие ошибки запрещают DEV; предупреждения нужно явно признать просмотренными.
3. Перед DEV сервис сравнивает базовый commit, текущий `main` и черновик. Независимые изменения объединяются, пересечение останавливается как конфликт.
4. Сервис создаёт commit с точными JSON и `.deploy/dev.json`, ждёт все DEV workflows; скрипт Actions записывает конфиги в Roblox и перечитывает каждый из них.
5. Только после успешных Actions создаётся проверенный DEV snapshot; тестировщик нажимает «Подтверждаю тестирование в игре».
6. PROD доступен только для того же `versionId`, проверенного в настоящем DEV.
7. PROD требует отдельного `ALLOW_REAL_PROD=true` и фразу `DIG GET STRONGER / PROD`; локально флаг оставлен выключенным.

Откат копирует старый снимок в новую версию с `source=rollback`; история не удаляется. Одинаковые checksum разрешены, потому что событие отката обязано иметь собственную запись.

## Подключение GitHub и Roblox

`GitHubPublisher` находится в `lib/publishing.ts`. Он использует Git Data API для одного commit без локального изменения рабочей копии, защищается от сдвига `main`, сохраняет независимые удалённые правки и ждёт DEV/PROD workflow по SHA commit. Старый `MockPublisher` оставлен только для изолированного unit-теста и никогда не выбирается API-маршрутом приложения.

В репозитории пока есть по два DEV и PROD workflow; сервис ждёт все сработавшие workflow соответствующей среды. После подтверждения владельца дубли можно удалить отдельно.

`GITHUB_TOKEN` и `ROBLOX_API_KEY` должны существовать только в зашифрованном secret store платформы. Их нельзя передавать клиенту, класть в D1, `.env.example`, JSON или audit log.

## Backup и восстановление

Импортированное расписание сохранено: ежедневно в `02:00 Europe/Moscow`. Основной пояс владельца — `Europe/Lisbon`; оба значения видны и редактируются в разделе команды. Существующий `.github/workflows/daily-config-backup.yml` продолжает копировать GitHub `configs` в `backlog`.

Для базы сервиса:

```bash
pnpm db:backup --local
# Только после настройки удалённой D1:
pnpm db:backup --remote
```

SQL-файлы пишутся в игнорируемый `backups/`. Планировщик платформы должен запускать remote-команду в импортированное время. Проверяйте восстановление минимум ежемесячно в отдельную базу:

```bash
pnpm exec wrangler d1 execute <RESTORE_DB> --remote --file backups/<snapshot>.sql
```

## Формулы и ограничения

Подтверждено только:

- средняя цена предмета `Σ(weight / Σweight × sellPrice)`;
- целостность пулов `Σweight = 100`;
- аналитические отношения роста между соседними комнатами.

В репозитории найден серверный загрузчик `ConfigService.lua`, но не игровой генератор физических предметов. Поэтому карта трактует нормализованный `weight` как шанс одной выборки. Условный расчёт `1 - (1 - p)^n` для 7–8 появлений скрыт по умолчанию и включается только после явного подтверждения владельцем независимых попыток с возвращением; это подтверждение хранится локально и не попадает в игровой JSON.

Средний доход комнаты использует 7.5 предмета только как видимое допущение. Не найдены потребители, подтверждающие итоговую силу, объединение питомцев, бонусы rebirth/arena/upgrades, число ударов, время блока/слоя/комнаты и время покупки. Эти поля остаются «формула не подключена». Подробные доказательства и риски: [AUDIT.md](AUDIT.md).

Сервис сохраняет точное десятичное значение (например, `10000000000000000` и `1.3e+30`) без округления JavaScript. После загрузки в Roblox Luau число становится double, поэтому точность целой части очень больших значений ограничена уже игровой платформой.
